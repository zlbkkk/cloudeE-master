# UI测试用例去重功能需求文档

## 1. 项目概述

### 1.1 背景
当前系统在生成UI测试用例时，由于多个数据来源（后端注释、旧版前端、新版前端）提供了不同准确度的菜单路径，导致生成的测试用例存在重复和信息冗余问题。

### 1.2 问题描述
- 同一个组件在不同前端项目中被使用，但菜单路径不同
- 后端注释提取的菜单路径没有端口信息
- 旧版前端（`beehive-order-finance-frontend`）没有端口前缀
- 新版前端（`beehive-order-finance-frontend-dev-2.25.0`）有端口前缀
- 导致生成的测试用例看起来有重复，有些有端口信息，有些没有

### 1.3 目标
实现智能去重逻辑，确保生成的UI测试用例：
1. 没有完全重复的测试用例
2. 优先保留信息更完整的测试用例（有端口前缀的）
3. 优先保留前端扫描的结果（比后端注释更准确）
4. 相同组件+相同API，只保留最准确的一个

## 2. 功能需求

### 2.1 去重规则

#### 2.1.1 唯一性判断标准
两个测试用例被认为是重复的，当且仅当：
- **组件名称相同** (`component_name`)
- **API路径相同** (`api_path`)
- **HTTP方法相同** (`api_method`)

#### 2.1.2 优先级规则
当发现重复的测试用例时，按以下优先级保留：

**优先级1：端口信息完整性**
- 有端口前缀（如 `[核企端]`）> 无端口前缀

**优先级2：数据来源**
- 新版前端扫描 > 旧版前端扫描 > 后端注释提取

**优先级3：菜单路径完整性**
- 有完整菜单路径 > 只有部分菜单路径 > 无菜单路径

**优先级4：行号（作为最后的判断标准）**
- 行号较小的（代码中较早出现的）

### 2.2 去重位置

去重逻辑应该在以下位置实现：

#### 选项A：在测试用例生成器中实现（推荐）
- 位置：`test_case_generator.py` 的 `generate_test_cases_batch()` 方法
- 优点：
  - 集中处理，逻辑清晰
  - 可以在生成测试用例后立即去重
  - 不影响AI分析流程
- 缺点：
  - 需要修改测试用例生成器

#### 选项B：在AI分析器中实现
- 位置：`ai_analyzer.py` 的 `analyze_with_llm()` 方法
- 优点：
  - 可以在传递给AI之前就去重，减少AI处理的数据量
- 缺点：
  - 需要在多个地方处理去重逻辑
  - 可能影响AI分析的准确性

#### 选项C：在runner中实现
- 位置：`runner.py` 的 `run_analysis()` 方法
- 优点：
  - 可以在最终生成报告前去重
  - 不影响前面的分析流程
- 缺点：
  - 去重时机较晚，可能已经生成了大量重复数据

**推荐方案：选项A（在测试用例生成器中实现）**

### 2.3 去重算法

#### 2.3.1 数据结构
使用字典存储已见过的测试用例：
```python
seen_cases = {}  # key: (component_name, api_path, api_method), value: TestCase
```

#### 2.3.2 算法流程
1. 遍历所有待生成的测试用例
2. 对每个测试用例，计算唯一键：`(component_name, api_path, api_method)`
3. 如果键不存在于 `seen_cases`，直接添加
4. 如果键已存在，比较优先级：
   - 如果新测试用例优先级更高，替换旧的
   - 否则，保留旧的，丢弃新的
5. 返回去重后的测试用例列表

#### 2.3.3 优先级计算
为每个测试用例计算一个优先级分数：
```python
def calculate_priority_score(test_case_info):
    score = 0
    
    # 端口信息（权重：100）
    if has_port_prefix(test_case_info['menu_path']):
        score += 100
    
    # 数据来源（权重：50）
    if is_from_new_frontend(test_case_info['file_path']):
        score += 50
    elif is_from_old_frontend(test_case_info['file_path']):
        score += 30
    # 后端注释：0分
    
    # 菜单路径完整性（权重：20）
    if test_case_info['menu_path']:
        menu_depth = test_case_info['menu_path'].count('>')
        score += min(menu_depth * 5, 20)
    
    # 行号（权重：-0.001，越小越好）
    score -= test_case_info['line_number'] * 0.001
    
    return score
```

## 3. 非功能需求

### 3.1 性能要求
- 去重操作应该在1秒内完成（对于1000个测试用例）
- 不应显著增加整体分析时间

### 3.2 可维护性
- 去重逻辑应该独立封装，便于测试和修改
- 优先级规则应该可配置

### 3.3 日志记录
- 记录去重前后的测试用例数量
- 记录被丢弃的测试用例信息（用于调试）
- 记录优先级比较的详细信息

## 4. 验收标准

### 4.1 功能验收
- [ ] 相同组件+相同API的测试用例只保留一个
- [ ] 保留的测试用例有端口前缀（如果存在）
- [ ] 保留的测试用例来自新版前端（如果存在）
- [ ] 保留的测试用例有完整的菜单路径（如果存在）

- [ ] 代码注释完整
- [ ] 更新相关文档

## 6. 风险和缓解措施

### 6.1 风险1：去重逻辑过于激进
- **描述**：可能会误删除有用的测试用例
- **缓解措施**：
  - 详细的日志记录，便于追踪被删除的测试用例
  - 提供配置选项，允许调整去重规则
  - 在测试环境充分验证

### 6.2 风险2：性能问题
- **描述**：大量测试用例可能导致去重操作耗时过长
- **缓解措施**：
  - 使用高效的数据结构（字典）
  - 性能测试和优化
  - 如果必要，考虑并行处理

### 6.3 风险3：优先级规则不合理
- **描述**：优先级规则可能不符合实际需求
- **缓解措施**：
  - 与用户充分沟通，确认优先级规则
  - 提供配置选项，允许调整权重
  - 持续收集反馈，迭代优化

本文档总结了跨项目影响分析系统已实现的所有跨服务调用识别场景。

## 一、已实现的调用方式

### 1. Dubbo RPC 调用 ✅ (最高频场景)

**优先级**: ⭐⭐⭐⭐⭐ (最重要)

**实现位置**: 
- `backend/analyzer/analysis/static_parser.py` - `find_usages` 方法
- `backend/analyzer/analysis/multi_project_tracer.py` - 跨项目追踪逻辑

**识别原理**:
1. 通过 `import` 语句识别接口引用
2. 扫描文件中所有包含该类名的行（包括 `@DubboReference` 注解的字段声明）
3. 追踪方法调用链，直到找到 Controller 层的 API 接口

**代码示例**:
```java
// common-api 项目 - 定义接口
package com.example.common.service;

public interface OrderService {
    String getOrderStatusText(Long orderId);
    void updateOrderStatus(Long orderId, String status);
}

// service-a 项目 - 实现接口
package com.example.servicea.service;

@Service
public class OrderServiceImpl implements OrderService {
    @Override
    public String getOrderStatusText(Long orderId) {
        // 实现逻辑
        return "已发货";
    }
}

// service-b 项目 - 通过 Dubbo 调用
package com.example.serviceb.service;

@Service
public class NotificationService {
    @DubboReference  // Dubbo RPC 注入
    private OrderService orderService;
    
    public void sendOrderNotification(Long orderId) {
        // 跨服务调用
        String status = orderService.getOrderStatusText(orderId);
        // 发送通知
    }
}
```

**识别结果**:
- 类型: `class_reference` (类引用)
- 类型: `method_call` (方法调用)
- 类型: `api_call` (如果追踪到 Controller)

**测试场景**: 
- 修改 `service-a` 的 `OrderServiceImpl.getOrderStatusText` 方法
- 应识别出 `service-b` 的 `NotificationService` 中的调用
- 应追踪到 `service-b` 的 `NotificationController` 的 API 接口

---

### 2. Feign HTTP 调用 ✅

**优先级**: ⭐⭐⭐⭐

**实现位置**: 
- `backend/analyzer/analysis/multi_project_tracer.py` - 跨项目分析逻辑
- `backend/analyzer/analysis/static_parser.py` - `find_usages` 方法

**识别原理**:
1. 识别 `@FeignClient` 注解定义的接口
2. 通过 `@Autowired` 或 `@Resource` 识别注入点
3. 追踪方法调用

**代码示例**:
```java
// service-b 项目 - 定义 Feign 客户端
package com.example.serviceb.client;

@FeignClient(name = "service-a", path = "/api/users")
public interface UserClient {
    @GetMapping("/{userId}")
    UserDTO getUser(@PathVariable Long userId);
    
    @PostMapping
    UserDTO createUser(@RequestBody UserDTO user);
}

// service-b 项目 - 使用 Feign 客户端
package com.example.serviceb.service;

@Service
public class NotificationService {
    @Autowired  // Spring 依赖注入
    private UserClient userClient;
    
    public void sendUserNotification(Long userId) {
        // 跨服务 HTTP 调用
        UserDTO user = userClient.getUser(userId);
        // 发送通知
    }
}
```

**识别结果**:
- 类型: `class_reference` (Feign 客户端引用)
- 类型: `method_call` (方法调用)

**测试场景**:
- 修改 `service-a` 的 `UserController.getUser` 方法
- 应识别出 `service-b` 的 `UserClient` 接口定义
- 应追踪到 `NotificationService` 中的调用

---

### 3. RabbitMQ 消息队列 ✅

**优先级**: ⭐⭐⭐⭐

**实现位置**: 
- `backend/analyzer/analysis/rabbitmq_analyzer.py` - RabbitMQ 专用分析器
- `backend/analyzer/analysis/multi_project_tracer.py` - `_find_rabbitmq_impacts` 方法

**识别原理**:
1. **生产者识别**: 扫描 `rabbitTemplate.convertAndSend()` 调用
2. **消费者识别**: 扫描 `@RabbitListener` 和 `@RabbitHandler` 注解
3. **匹配逻辑**: 根据 exchange、routingKey 和 queue 的关系匹配生产者和消费者

**代码示例**:
```java
// service-a 项目 - 消息生产者
package com.example.servicea.service;

@Service
public class OrderServiceImpl {
    @Autowired
    private RabbitTemplate rabbitTemplate;
    
    public void createOrder(OrderDTO order) {
        // 业务逻辑
        order.setStatus("CREATED");
        
        // 发送 RabbitMQ 消息
        rabbitTemplate.convertAndSend(
            "order.exchange",      // exchange
            "order.created",       // routing key
            order                  // message
        );
    }
}

// service-b 项目 - 消息消费者
package com.example.serviceb.listener;

@Component
public class OrderEventListener {
    
    @RabbitListener(queues = "order.notification.queue")
    public void handleOrderCreated(OrderDTO order) {
        // 处理订单创建事件
        System.out.println("收到订单创建消息: " + order.getId());
        // 发送通知
    }
    
    @RabbitListener(queues = "order.notification.queue")
    @RabbitHandler
    public void handleOrderUpdated(OrderDTO order) {
        // 处理订单更新事件
    }
}
```

**识别结果**:
- 类型: `rabbitmq_producer` (消息生产者)
  - 包含: exchange, routing_key, message_type
- 类型: `rabbitmq_consumer` (消息消费者)
  - 包含: queue, consumer_class, consumer_method

**测试场景**:
- 修改 `service-a` 的 `OrderServiceImpl.createOrder` 方法
- 应识别出 RabbitMQ 消息发送
- 应在 `service-b` 中找到对应的消息消费者

### 4. Spring 依赖注入 ✅

**优先级**: ⭐⭐⭐⭐⭐

**实现位置**: 
- `backend/analyzer/analysis/static_parser.py` - `find_usages` 方法

**识别原理**:
1. 通过 `import` 识别类引用
2. 扫描 `@Autowired`、`@Resource` 注解的字段
3. 扫描构造函数注入

**代码示例**:
```java
// 字段注入
@Service
public class UserService {
    @Autowired
    private OrderService orderService;
    
    @Resource
    private NotificationService notificationService;
}

// 构造函数注入
@Service
public class UserService {
    private final OrderService orderService;
    
    @Autowired
    public UserService(OrderService orderService) {
        this.orderService = orderService;
    }
}

// Setter 注入
@Service
public class UserService {
    private OrderService orderService;
    
    @Autowired
    public void setOrderService(OrderService orderService) {
        this.orderService = orderService;
    }
}
```

**识别结果**:
- 类型: `class_reference` (类引用)
- 类型: `method_call` (方法调用)

## 二、方法重载识别 ✅

**实现位置**: 
- `backend/analyzer/analysis/api_tracer.py` - `_parse_file_for_calls` 方法
- 方法签名提取和匹配逻辑

**功能说明**:
系统能够区分同名但参数不同的重载方法，避免误报。

**代码示例**:
```java
public interface OrderService {
    // 重载方法 1: 无参数
    String getOrderStatusText(Long orderId);
    
    // 重载方法 2: 带参数
    String getOrderStatusText(Long orderId, String language);
}

// 调用时能够精确匹配
orderService.getOrderStatusText(123L);           // 匹配方法 1
orderService.getOrderStatusText(123L, "zh-CN");  // 匹配方法 2
```

**匹配策略**:
- 参数数量必须相同
- 能推断的类型必须匹配
- 无法推断的类型认为可能匹配（宽松策略）

## 三、递归追踪 ✅

**实现位置**: 
- `backend/analyzer/analysis/multi_project_tracer.py` - `_find_recursive_impacts` 方法

**功能说明**:
系统能够递归追踪调用链，直到找到 Controller 层的 API 接口。

**追踪流程**:
```
变更的类/方法
    ↓
Service 层调用
    ↓
另一个 Service 层调用
    ↓
Controller 层 (API 接口)
```

**示例**:
```java
// 1. 变更的类
@Service
public class OrderServiceImpl {
    public String getOrderStatusText(Long orderId) {
        return "已发货";  // 修改这里
    }
}

// 2. Service 层调用
@Service
public class NotificationService {
    @DubboReference
    private OrderService orderService;
    
    public void sendNotification(Long orderId) {
        String status = orderService.getOrderStatusText(orderId);
    }
}

// 3. Controller 层 (最终追踪到这里)
@RestController
public class NotificationController {
    @Autowired
    private NotificationService notificationService;
    
    @PostMapping("/api/notifications/order/{orderId}")
    public void sendOrderNotification(@PathVariable Long orderId) {
        notificationService.sendNotification(orderId);
    }
}
```

**识别结果**:
- 最终报告 API: `POST /api/notifications/order/{orderId}`
- 调用链深度: 最多 5 层

## 七、注意事项

1. **Dubbo 是最高频场景**: 优先测试和验证 Dubbo RPC 调用
2. **方法签名很重要**: 系统会提取方法签名来区分重载方法
3. **递归追踪深度**: 默认最多追踪 5 层调用链
4. **日志已清理**: 调试日志已清理，只保留必要的 logger 日志
5. **RestTemplate 不推荐**: 虽然已实现，但实际项目中不再考虑此场景
